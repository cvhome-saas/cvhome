# Design System: cvhome Console

## Overview

**Creative North Star: “The Controlled Territory”**

cvhome presents multi-market commerce as one calm, governed territory. Deep forest surfaces create authority and continuity; precise emerald signals identify actions, status, emphasis, and live commerce without turning the page into a generic neon dashboard.

The system has **one surface treatment and two densities.** Public marketing, account access, and authenticated administration all sit on the same deep forest canvas with the same emerald signals, the same Inter type, the same focus ring, and the same restrained motion. What changes between them is density, not palette: marketing is spacious (generous radii, light expansive headlines, wide sections) while the console is compact (tight radii, the sturdier `operations*` type roles, dense rows). A control never changes colour because of where it lives.

**Key Characteristics:**

- Deep forest canvas with a tightly controlled emerald signal palette, everywhere.
- Restrained Inter typography: expansive light headlines, firm compact labels.
- Broad centered sections and responsive grids that suggest territory and scale.
- Flat translucent surfaces with borders; lift appears mainly during interaction.
- Pill actions and controls paired with softly rounded cards and fields.
- Density, not colour, distinguishes the operational workspace from marketing.

### Named Rules

**The Emerald Signal Rule.** Emerald communicates action, state, or deliberate emphasis. Keep most of every screen forest and neutral so the signal retains authority.

**The Themed Surface Rule.** No component decides its own light or dark. A surface is built from the semantic tokens — `--background`, `--card`, `--border`, `--foreground` — and the active theme decides what those mean. Forest and Midnight are dark and stack translucent white over a deep field; Daylight is light and stacks translucent near-black over a pale one; Light is lighter still and makes its panels *opaque*, brighter than the page they sit on. A component that hardcodes `rgb(255 255 255 / 6%)` works in two themes and breaks in the other two; a component that uses `--input` works in all of them, and in the next one.

This replaces the former Dark Territory Rule, which held that the world was dark by construction. Two of the four themes still are, and Forest remains the default and the brand's face on marketing and authentication — but "dark" is now a property of a theme, not of the system.

**The One-World Rule.** There is a single surface treatment *at a time*. Marketing, authentication, and the console share one canvas, one palette, and one focus ring; only density changes between them. Switching theme switches all of them together — the choice is stored per operator and applied to the document root, so signing out onto the marketing page does not change surface underneath them.

**The Stable Vocabulary Rule.** Chrome may be re-hued; data may not. `--chart-1` through `--chart-6` name the same six hues in every theme, because "amber means pending" is something an operator learns once and should not have to relearn because they changed the colour of their sidebar. What does move per theme is `--chart-N-foreground`, the ink, which has to stay legible against a background that just changed. Colour also remains redundant with a label, value, or position in every theme.

**The Token Rule.** Every colour, radius, shadow, spacing step, and type step is a token, and every token name is a standard Tailwind one. A literal hex value in a stylesheet is a defect — if a value is missing, add it to the theme. The system is three files:

- `src/styles/theme.css` — primitives and scales on standard Tailwind keys (`--color-*`, `--text-*`, `--radius-*`, `--spacing-*`, `--breakpoint-*`). Tailwind's own palette is used as-is except for the brand steps, which are pinned; only the `forest` and `sage` ramps are authored outright.
- `src/styles/theme-forest.css`, `-midnight.css`, `-daylight.css`, `-light.css` — the identities, as semantic tokens in the shadcn/tweakcn vocabulary. **These are the only files that assign a colour to a role.**
- `src/styles/theme-bridge.css` — re-exports those into Tailwind's namespaces (`bg-background`, `border-border`) and composes the type roles.

Components reference the semantic layer (`var(--border)`, `bg-muted`), never a primitive. TypeScript that must paint outside the DOM — echarts, jsPDF — reads the same tokens back off the document through `THEME`, so there is no second copy of the palette.

### Themes

| Theme | Surface | Accent | Scheme |
|---|---|---|---|
| **Forest** (default) | Deep green | Emerald | Dark |
| **Midnight** | Slate | Indigo | Dark |
| **Daylight** | Near-white | Emerald | Light |
| **Light** | White on grey | Emerald | Light |

A theme is exactly one `[data-theme='…']` block and nothing else. Forest also claims bare `:root`, which makes it the base every other theme overrides and the value any incomplete theme falls back to — so it must stay first in the cascade and must stay complete. `theme.service.spec.ts` fails the build if a theme leaves a token unset, which on Daylight would mean a dark colour on a light page.

Adding one is three steps: a stylesheet imported after Forest in `styles.css`, an entry in `CONSOLE_THEMES`, and the id added to the `themes` array in the pre-paint script in `index.html` — a theme missing from that array is stored correctly and then silently rejected on the next load, which renders as "my theme keeps resetting to Forest". Its `shell.theme.<id>.{label,hint}` keys go in every locale file. Nothing else in the app changes — components already speak only in semantic tokens, and `THEME` re-reads them on switch so canvas-drawn surfaces repaint themselves.

The operator's choice is stored in `localStorage` and applied by an inline script in `index.html` before the first paint. It has to be inline and it has to be there rather than in Angular: the app boots after the document renders, so applying it in a service would show a frame of Forest first. The default is deliberately Forest rather than the operating system's `prefers-color-scheme` — Forest is the brand's face on marketing and authentication, and Daylight is a choice an operator makes rather than one their OS makes for them.

Daylight is not an inversion of Forest. Alphas flip from white-over-dark to near-black-over-light *and* drop in strength; the categorical inks move four steps (`-300` → `-700`) because the -300s exist to glow on a dark field; the text ladder compresses from five steps to four, because on white everything below `sage-600` falls under 3:1. The one pairing that does not change is `--primary` with `--primary-foreground`: emerald with near-black ink, because emerald with white ink is 2.3:1 and because a control should not change colour based on where it lives.

Light is not a re-hue of Daylight either; the two differ on the only question a light workspace really has, which plane is brightest. Daylight keeps the dark themes' structure and lightens it — the canvas is near-white and a panel is a tint *on top of* it, so panels sit fractionally darker and read as cards because of their edge. Light inverts that, following `store-core/console-template`: the canvas is grey, every panel is opaque white, and a card reads because it is *brighter* than its surroundings. That is why `--muted` is the one token in the system that is an opaque colour in one theme and an alpha in the other three — nothing stacked on a light field can come out lighter than the field, so a panel that must outrank its page cannot be translucent. Its neutral is slate throughout, Tailwind's stock ramp as shipped, exactly as Midnight uses it.

Adopting the template did not mean copying it. It paints white on emerald-500 for primary buttons, which is 2.3:1; the `--primary`/`--primary-foreground` pairing above wins, and Light keeps near-black ink. Its lightest label ink, slate-400, is 2.8:1 on white; those jobs go to slate-500, the lightest step clearing 4.5:1, which compresses the ladder the same way Daylight's is compressed.

### Operational Palette

The console draws from the same tokens as marketing. Its distinct character comes from density and from a small set of tokens intended for dense work:

- **Muted** (`--muted`, white 2% on the dark themes): Cards, panels, the navigation rail. A card reads as a card because of its hairline edge, not because it is brighter — except on Light, where the token is opaque white and brightness is exactly what it reads by.
- **Input** (`--input`, white 6% on the dark themes): Hover fills, icon tiles, inset wells. **A tint stacked on a panel is always this, never `--muted`** — the two are a hair apart on Forest, so the distinction was easy to miss until Light made `--muted` opaque and every rule that had reached for the wrong one turned invisible.
- **Track** (`--track`, white 18% on the dark themes): The unfilled portion of a chart — donut remainder, bar baseline, progress track. Deliberately far above the hover fill because it has to read as data, not as an inset.
- **Compact radii** (`sm` 4px through `xl` 12px): The console's shape vocabulary, against marketing's `2xl`/`3xl` (16–20px).
- **Categorical set** (`--chart-N` fill, `--chart-N-foreground` ink, `--chart-N-wash` backing): Six slots — emerald, blue, cyan, amber, red, violet — distinguish series or operational conditions. Always pair colour with a label, value, icon, or position — never colour alone.

## Typography

**Display Font:** Inter (with UI system fallbacks)

**Body Font:** Inter (with UI system fallbacks)

**Label Font:** Inter (with UI system fallbacks)

**Character:** One restrained sans-serif family carries the system. Personality comes from contrast: low-weight, tightly tracked display type versus sturdy, widely tracked uppercase labels.

### Hierarchy

- **Display** (300, `clamp(3.25rem, 7.1vw, 5.75rem)`, `0.98`): First-viewport declarations; balanced lines, with a stronger emerald phrase when needed.
- **Headline** (300, `clamp(2.4rem, 5vw, 3.5rem)`, `1.12`): Section propositions, normally capped near `20ch`.
- **Title** (600, `1.25rem`, compact tracking): Card and pillar names.
- **Body** (350, generally `1rem`, `1.7–1.75`): Explanations and persuasive copy; prominent introductions stay near `42–47ch`.
- **Label** (700, `0.625–0.6875rem`, `0.07–0.1em`, uppercase): Status, metric captions, plan names, form labels, and market metadata.
- **Auth Headline** (300, `clamp(2.6rem, 4vw, 3rem)`, `1.12`): Task-oriented account-access propositions inside a split viewport.
- **Prominent Body** (350, `1.0625rem`, `1.75`): Short auth-story introductions, held near `34ch`.
- **Compact Body** (350, `1rem`, `1.6`): Benefit lists and dense operational action copy.
- **Caption** (350–700, `0.8125rem`): Tabs, options, links, and trust statements; weight supplies hierarchy without increasing size.
- **Micro** (600, `0.75rem`, `1.5`): Field labels, badges, dividers, legal notes, and inline system feedback.

### Named Rules

**The Quiet Authority Rule.** Headings earn scale through space and light weight. Do not make large headings heavy; reserve heavier weight and emerald for the decisive phrase.

Operational dashboards deliberately tighten the ladder: page titles are bold at `1.75rem`; panel titles sit near `1.0625rem`; controls and row content cluster around `0.75–0.875rem`; uppercase navigation and metric labels use `0.6875rem` (`text-3xs`) with open tracking. Density comes from smaller roles and firm weights, never from illegibly tight line height.

## Layout

The primary content frame is `1100px`, centered on the forest canvas. Sections use `7rem 3rem` desktop padding; the hero is broader and taller, with a `1050px` content measure and at least `680px` height. Section headings pair a flexible proposition with compact evidence aligned to its baseline.

Use repeated grids to express breadth: four columns for merchant proof, three for pillars, reviews, and plans, and two for contact. At `900px`, navigation becomes a drawer, four-column grids reduce to two, three-column grids stack, and sections tighten to `5rem 1.5rem`. At `600px`, merchant grids stack, actions become full-width columns, split headings become vertical, and form rows become single-column.

Marketing spacing is generous and rhythmic: `1–1.5rem` within controls and cards, `2.5–4.5rem` between a heading and its proof, and `5–7rem` between major narrative regions. The first of those is the tokenised range — `--spacing-group` through `--spacing-gutter`; the wider narrative measures stay literals, because they are page composition rather than component rhythm.

Account-access surfaces use a balanced two-panel viewport: a story region and a centered entry region each occupy half the width, while the form stays capped near `26rem`. At `800px`, the regions stack and the form may widen to `32rem`; at `480px`, supporting benefits yield to the primary task and form padding tightens. This split is an authentication pattern, not a replacement for the centered marketing frame.

**The Story-and-Entry Rule.** In authentication flows, keep product reassurance and account entry as peer regions on wide screens, then place the story before the form when stacked.

Operational dashboards use a persistent two-column shell: `280px` navigation and a fluid work area. The rail may collapse to `76px`; below `1180px` it collapses automatically, metrics reduce from four to two columns, and split dashboard rows stack. Below `768px` (`md`), navigation becomes an off-canvas drawer with a scrim and fixed launcher. Below `480px`, metrics become one column and charts compress without losing labels.

Use a compact `1–1.5rem` dashboard rhythm. White work surfaces group related information; the cool gray canvas separates regions. Illustrative or placeholder values must carry a nearby visible label such as “Illustrative data”; never present synthetic commerce metrics as live production truth.

**The Operational Continuity Rule.** Navigation persists on wide screens, collapses before content becomes cramped, and becomes a drawer on mobile; the information architecture stays the same in every mode.

## Elevation & Depth

The system is flat at rest. Depth comes from tonal forest layers, translucent white fills, fine low-opacity borders, the sticky header’s blur, and one atmospheric radial glow. Shadows appear primarily as state feedback: buttons and merchant cards lift on hover rather than floating continuously.

### Shadow Vocabulary

- **Primary Lift** (`--lift-primary`, `0 12px 30px rgb(16 185 129 / 25%)`): Primary-button hover only.
- **Lift** (`--lift`, `0 20px 45px rgb(0 0 0 / 20%)`): Interactive merchant-card hover only.
- **Atmospheric Glow** (`radial-gradient(circle, rgb(16 185 129 / 27%), transparent 68%)` with `blur(22px)`): Hero atmosphere; never a generic card effect.

### Named Rules

**The Flat-at-Rest Rule.** Static surfaces use tone and borders. Elevation is an interaction response or a single compositional atmosphere.

In the operational subsystem, white surfaces use a structural `1px` slate border and a minimal resting shadow (`0 1px 2px rgb(18 18 23 / 5%)`). Popovers may use a stronger overlay shadow; interactive metric cards may lift on hover. Do not import the dark world’s glow or glass effects into admin workspaces.

## Shapes

One scale, `rounded-sm` through `rounded-3xl` (4/6/8/12/16/20px), plus `rounded-full` for pills. In the dark world, controls use the pill silhouette, content containers use `2xl` (16px), and fields and channel rows use `lg`–`xl`. The operational subsystem stays at the compact end: `sm` for compact labels, `md` for fields and small actions, `lg` for rows and icon tiles, and `xl` for primary work surfaces and the navigation rail. Pills remain appropriate for badges and counts; circles are reserved for avatars, indicators, and the mobile navigation launcher.

## Components

### Buttons

- **Shape:** Full pill, `48px` minimum height, with `0.8rem 1.5rem` padding.
- **Primary:** Territory Emerald fill and border with Forest Ink text; bold, centered, and concise.
- **Hover / Focus:** Translate upward `2px`, brighten to Live Emerald, and add Action Lift. Keyboard focus uses a `3px` Focus Mint outline offset by `4px`.
- **Secondary:** Transparent forest field, subtle white border, and Cool White text; emerald tint and border on hover without shadow.
- **Compact:** Header actions may reduce to `38px` minimum height and `0.55rem 1.05rem` padding.

### Chips

- **Style:** Pill border, transparent background, compact semibold text.
- **State:** Inactive uses Quiet Sage and a translucent white border; selected uses a translucent emerald field, stronger emerald border, and pale emerald text.

### Cards / Containers

- **Corner Style:** `16px` for stores, reviews, plans, and forms; `14px` for compact channel rows.
- **Background:** Usually `rgb(255 255 255 / 2%)`; forms use Forest Surface and featured plans use a restrained emerald tint.
- **Shadow Strategy:** None at rest. Only interactive merchant cards lift.
- **Border:** `1px` translucent white, strengthened with emerald for featured or hover states.
- **Internal Padding:** Roughly `1.2rem` for compact cards and `1.7–2.2rem` for reviews, plans, and forms.

### Inputs / Fields

- **Style:** `10px` radius, translucent white field, `1px` low-contrast border, and `0.75rem 0.85rem` padding.
- **Focus:** Live Emerald border plus a faint emerald field tint; global keyboard focus remains visible.
- **Disabled / Complete:** Replace the solid action fill with a subdued emerald tint while retaining legible pale-emerald text.

### Authentication Panel

- **Composition:** A `16px` forest-glass form card centered in the entry half of the viewport, paired with a full-height story panel.
- **Switcher:** A pill track with equal-width account-action tabs; the active tab uses Territory Emerald and Forest Ink.
- **Density:** Fields follow a compact `1rem` rhythm. Supporting sign-in options share one row until the narrowest viewport.
- **Progressive disclosure:** On very small screens, remove the benefit list before compressing the form or its tap targets.

### Navigation

The sticky header is a blurred translucent forest plane with a fine divider. Links are compact semibold sage and brighten to white on hover. Below `900px`, use a full-width vertical drawer immediately beneath the `72px` header; keep the primary action visually distinct at the end.

Operational navigation is a white persistent rail on the cool gray canvas. Active items use a pale emerald field and dark emerald text; hover uses slate-100. Preserve labels at full width, icons only at `76px`, and restore the full labeled rail in the mobile drawer. Toolbars are white `12px` surfaces with breadcrumb, search, notifications, language, and profile actions that progressively simplify on narrow screens.

### Status and Metrics

Status uses an uppercase pill with a pulsing emerald dot. Metrics use large, low-weight white values over small uppercase sage captions. Motion is calm and optional; honor `prefers-reduced-motion` globally.

## Do's and Don'ts

### Do:

- **Do** preserve the forest-to-emerald hierarchy: dark territory first, signal color second.
- **Do** use generous vertical space and centered `1100px` content regions to communicate breadth and control.
- **Do** keep body copy measured and high contrast, especially over translucent surfaces.
- **Do** preserve visible focus, semantic controls, tap-friendly dimensions, and the reduced-motion override.
- **Do** author every design value in `src/styles/theme-forest.css` and consume it as a token; the marketing page is the reference implementation.
- **Do** distinguish the operational workspace by density — compact radii, the `operations*` type roles, tighter rows — never by changing the palette.
- **Do** label illustrative dashboard data visibly and keep semantic chart colors redundant with text or structure.

### Don't:

- **Don't** hardcode a light or dark value — no white-alpha overlay, no black shadow, no "on dark" ink. Use the semantic token and let the theme decide; a value that assumes darkness breaks Daylight, and one that assumes lightness breaks the other two.
- **Don't** re-hue the categorical scale in a new theme. Chrome is brand; `--chart-N` is vocabulary.
- **Don't** use emerald decoratively across large areas; it marks action, state, or intentional emphasis.
- **Don't** make every surface float. Static cards remain border-and-tone layers without shadows.
- **Don't** replace restrained Inter typography with ornamental display faces or heavy oversized headings.
- **Don't** add busy motion; the established language is one slow atmospheric drift plus short tactile state transitions.
- **Don't** bring the atmospheric hero glow or oversized marketing type into dense operational workspaces; they share a palette, not a scale.
- **Don't** hardcode a hex value, radius, or shadow in a stylesheet — add it to the theme instead.
