# Client secrets: a fast hash, because a machine secret is not a password

One PR, `fix/client-secret-hashing`, one commit per phase, easiest first. Only `sso-core` and its callers change;
uaa and cua both run it. No other repo is touched. The owner has confirmed that tables and code may be dropped
and recreated freely, so no data migration is written.

## What was found (2026-09-13)

A load test of dev on AWS (`store-settings-load-20260913T073725Z`, cvhome-saas/load-testing#12) measured seller
sign-in (`seller:login-submit`) at a p95 of 1.8 s. uaa, one task with 0.25 vCPU, ran at 45–89 % CPU in exactly
the minutes the test's four sign-ins ran, and at about 1 % otherwise. The same sign-in on a full core answers in
255–282 ms (`docs/baseline.md` in load-testing).

The cost is bcrypt, measured with this repo's `spring-security-crypto` 7.1.0 on one core of an Apple-silicon laptop:

| Check | Where | CPU |
| --- | --- | --- |
| bcrypt strength 10 | a seeded demo user's password (`init-sql/data-*.sql` carry `$2a$10$` hashes) | 56 ms |
| bcrypt strength 12 | any password the app sets (`PasswordConfig`, `BCRYPT_STRENGTH = 12`) | 227 ms |
| bcrypt strength 12 | **every client secret**: `OAuth2ClientDatabaseInitializer.java:70` and `AdminClientService` hash with the same encoder | 227 ms |

A seller sign-in is one password check at the login form plus one client-secret check when the gateway exchanges
the code at `/oauth2/token` (`GraceAwareClientSecretAuthenticationProvider` keeps that to one bcrypt). That is
283–454 ms of CPU, which on 0.25 vCPU is 1.1–1.8 s before any queueing. Every service-to-service
`client_credentials` token request pays the 227 ms client-secret check as well. A shopper's sign-in through cua
runs the same code.

## Why bcrypt is the wrong tool for a client secret

bcrypt's work factor exists to slow down offline guessing of a **low-entropy human password** after a database
leak. The client secrets here are not guessable:

- Generated by uaa: 32 random bytes, Base64URL (`AdminClientService.java:112-113`), for create and rotate.
- Seeded on AWS: `secrets.token_urlsafe(32)` in cvhome-platform's bootstrap. Seeded locally: a committed
  32-character demo string.
- The one exception is `POST /api/v1/admin/clients/{id}/reset-secret`, which stores **a secret the operator
  chose** (`AdminClientService.resetSecret`, `ResetSecretRequest` with no validation at all).

Guessing a 256-bit random value is infeasible whatever the hash costs. So a salted SHA-256 gives these secrets the
same protection as bcrypt for microseconds instead of 227 ms, **provided no human-chosen secret remains**. User
passwords keep bcrypt at strength 12.

## Decisions

- **User passwords do not change.** bcrypt strength 12 stays for everything `PasswordService` and the user
  initializers hash.
- **A `ClientSecretEncoder` type for client secrets.** It is a `DelegatingPasswordEncoder` whose default is a
  salted SHA-256 (`{sha256}<salt>$<digest>`, 16 random bytes of salt, compared with `MessageDigest.isEqual`).
  bcrypt stays only as a verifier for rows hashed before this change. Spring Authorization Server 7.1's
  `ClientSecretAuthenticationProvider` calls `upgradeEncoding` and saves the client after a successful check, so
  each such row rewrites itself on its first sign-in; nothing else migrates. It is a type, not a second
  `PasswordEncoder` bean: a by-type `PasswordEncoder` injection keeps meaning the password encoder, the way this repo
  wires beans by the type that carries their behaviour. (Given the drop/create freedom, the bcrypt verifier could go
  too; it stays because it costs one map entry and spares dev a wipe of the registered-client table on deploy.)
- **The operator-chosen secret path is deleted.** The endpoint, `AdminClientService.resetSecret`, the SDK's
  `AdminClientClient.resetSecret`, ui-kit's `AdminClientService.resetSecret` and the `.http` block. No screen and
  no other repo calls it. Rotation, which generates the secret and keeps a grace window, is the only way to change
  a secret.
- **A configured client secret must be at least 32 characters.** `OAuth2ClientDatabaseInitializer` refuses to
  start otherwise, so a weak secret cannot enter through configuration either. The local demo secrets are 32
  characters; the AWS ones are 43.
- **Not in this PR:** CPU for uaa and cua on dev (a cvhome-platform change, if sign-in bursts matter there), and
  bcrypt's strength for passwords.

## Deviations as built

- **Load-test p95 replaced by single sign-in times.** `make platform-gateway-login PROFILE=load` runs at a fixed 30
  sign-ins a minute, which saturates a 0.25-CPU uaa in both builds: every sign-in also pays the user's bcrypt-12
  password check, about 0.45 s of that CPU. Its p95 is timeouts either way (28 in two minutes before, 14 after; 0
  completed sign-ins before, 15 after). The clean comparison is one sign-in at a time, `PROFILE=smoke`, five runs each.
- **One strength-12 check costs about 450 ms in the capped container**, not the 227 ms a warm JVM measured on a full
  host core. The token endpoint made one check per request before this change, not two; the sign-in difference
  (3.9 → 1.9 s at 0.25 CPU) accounts for exactly one.
- **The 32-character guard is proved by a unit test** (`OAuth2ClientDatabaseInitializerTest`), not a context boot. It
  runs in an `ApplicationReadyEvent` listener, and an exception there fails `SpringApplication.run`.
- **`ClientSecretEncoder` has a package-private constructor over another encoder.**
  `GraceAwareClientSecretAuthenticationProviderTest` uses it to keep its readable `{noop}` hashes and its
  one-match-per-request count.
- **The QA files' case counts were stale before this change** (uaa said 143 and has 163; cua said 25 and has 44).
  They now state the real counts.
- **cua is verified by unit and integration tests only.** It runs the same sso-core code; its QA case LGN-10 says so.

Tests:

- sso-core unit tests: 709 pass. They include `ClientSecretEncoderTest` (19) and new cases in
  `GraceAwareClientSecretAuthenticationProviderTest` (a live bcrypt hash is rewritten as `{sha256}`; a `{sha256}` one
  is not re-saved; a retired bcrypt hash authenticates inside its window and is never written back) and
